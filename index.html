Featured project

Pi hole DNS sinkhole on a Raspberry Pi

Problem: Ads and promotions on my home network, a Roku TV, YouTube, and a few other devices. My ISP Xfinity gateway would not let me set custom DNS, so a normal Pi hole install was not an option.

What I did: Made the Pi hole the network DHCP server (10.0.0.50 to 250) with a static IP of 10.0.0.16 over WiFi, and disabled DHCPv6 on the gateway so devices could not bypass filtering over IPv6. Stacked OISD and HaGeZi blocklists on top of the 75,994 domain base list, and wrote per device deny rules from live query logs.

Result: Filters DNS for 6 devices with 10 of 858 queries blocked in the first sample (1.2%). Roku promotions disappeared. YouTube ads did not: Pi hole works at the DNS level, and YouTube serves ads from the same domains as its content.

Pi hole findings

  • Full writeup: View repository on GitHub for setup notes, configs, and automation scripts.
  • The DHCP handover: Gateway would not allow custom DNS, so the Pi became the DHCP server (10.0.0.50 to 250). Disabled stateless and stateful DHCPv6 on the gateway to force all traffic through the IPv4 sinkhole since modern devices will bypass you over IPv6 if you do not.
  • Troubleshooting: Hit an apt lock conflict during setup because packagekitd was holding /var/lib/apt/lists/lock. Killed the process and moved on.
  • Filtering stack: 75,994 domain base list, plus OISD and HaGeZi via Group Management Adlists. Per device policies and exact deny rules built from live query inspection.
  • Known limitation: YouTube ads are not blockable at the DNS layer since ads and content come from the same domains. This is expected behavior, not a misconfiguration.
  • Next: Second Pi as failover DNS, and DNS over HTTPS upstream so the ISP can not see queries either.
